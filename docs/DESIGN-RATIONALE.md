# DESIGN RATIONALE — workflow-sm

> 这份文档解释"为什么这么设计",而不是"怎么用"。
> 它是护城河的说明书,也是拒接需求时的挡箭牌。
> 如果你提的功能不在这份文档的"做"的范畴里,大概率它属于"明确不做"。

---

## 一句话定位

**唯一一个把执行顺序做成硬约束、可断点恢复、且能跑在任意 MCP 客户端里的轻量工作流引擎。**

差异化靠三个"别人不做或做不纯粹"的点支撑:

1. **有状态执行层**(不是无状态配方图书馆)
2. **顺序是硬约束**(server 强制,不是 agent 自觉)
3. **纯 MCP,任意客户端可移植**(不绑死某个 agent 框架)

---

## 核心设计决策(每条都有"为什么不那么做")

### 决策 1:状态活在 server 端,不在 agent 上下文里

**做了**:每次工具调用,server 返回"现在该执行哪一步";agent 只负责执行 + 把结果报回来。进度、历史、活跃集全在 server 的 `RunState` 里。

**为什么不那么做**(把状态丢给 agent 自己维护):agent 的上下文会随对话增长被压缩/截断,工作流状态会丢。这正是 multica-ai issue #5972 指出的痛点:"without a stateful execution layer, workflows degrade as context windows fill up"。把状态放 server 端,工作流的正确性就和 agent 的上下文长度解耦了——这是断点恢复能成立的前提。

### 决策 2:顺序是硬约束(泛化 GUARD),不是软建议

**做了**:`report_step_result` 在 server 端校验"你报告的步必须在当前活跃集里",否则抛错。活跃集 = 当前正在跑的那些步(线性模式单步;并行模式同组多步)。跳步、乱序、重报已完成步、报不存在步——全部被拒。

**为什么不那么做**(给 agent 一个配方,让它自觉按顺序):agent 会"自作主张"——跳过它觉得没必要的步、伪造结果、重报已完成的步、打乱顺序。我们在 `test-agent-chaos.mjs` 里实测了这 4 类混乱,全部被 GUARD 挡住。如果顺序只是软约束,工作流就退化成"agent 想怎么跑就怎么跑",确定性归零。**硬约束是把"流程"和"对话"区分开的关键。**

### 决策 3:并行用 `group` 字段,不用表达式 / 依赖图

**做了**:YAML 里给连续的同 `group` 步骤打同一个组名,server 在激活 front 时把整组同时置为 running。组的边界由"定义顺序 + 连续同组名"确定——**纯结构性的,不需要求值任何表达式**。

**为什么不那么做**(上 DAG / 依赖图 / `depends_on` / `when` 条件表达式):
- 一旦引入"步骤 A 依赖步骤 B 的输出求值",就需要一个**表达式引擎**(类似 Temporal/Airflow 的 `${{ }}` 或 `when:`)。这是复杂度的悬崖:要定义表达式语法、作用域、求值器、错误处理、调试工具。一个 200 行的引擎会膨胀成几千行。
- 更根本的是:**agent 天生就是最好的求值器**。与其让 server 解释"if output contains error then goto retry",不如让 agent 读 output 自己判断,然后用 `next_step_id` 显式告诉 server 跳到哪。这把"条件分支""循环""重试决策"全部统一成一个原语:`report_step_result(..., next_step_id)`。
- 这是和 Temporal/Airflow 这类声明式 DAG 引擎**错位竞争**的根基:它们求值表达式,我们求值 agent 的判断力。我们不抢它们的用户(需要确定性重放、超时、定时器的批处理场景),它们也不抢我们的(需要人在环里、agent 当编排者的交互场景)。

### 决策 4:重试是 server 管理的尝试计数,不是 agent 自己数

**做了**:YAML 里 `max_attempts: N`;agent report `status: "failure"` 时,server 递增该步的 `attempts`,未耗尽就让它重新 running 并提示"第 X/N 次重试";耗尽则该步 `failed`、整个 run `failed`。

**为什么不那么做**(让 agent 自己决定重试几次):agent 自己数重试,要么数错(上下文压缩后忘了第几次),要么无限重试(死循环)。让 server 用一个单调递增计数器管,重试次数是确定的、可观察的、有上限的。`test-retry-goto.mjs` 覆盖了"耗尽→failed"和"中途成功→继续"两条路径。

### 决策 5:断点恢复用文件,不用数据库

**做了**:每个 run 一个 JSON 文件,落在 `~/.workflow-runs/<run_id>.json`。每次状态变更后 `save()`;server 启动时 `loadAll()` 恢复全部历史 run。

**为什么不那么做**(上 SQLite / Postgres):单文件 JSON 对这个量级(个人/小团队的工作流实例)足够,且**零运维**——用户不需要装数据库、配连接、担心迁移。数据库的收益(并发、查询、规模)在这个产品的目标场景里不成立。当(且仅当)真实用户报告"我有上千个 run 要管理"时,再考虑迁移。**用复杂度换来了零运维,值得。**

### 决策 6:看板用"同进程内嵌 HTTP+SSE",不用独立监控进程

**做了**:MCP server 进程内,在 stdio transport 之外**额外**起一个 HTTP server(端口 7777,fallback)。engine 加一个 `onChange` 钩子,每次 `save()`(所有状态变更的汇聚点)触发,HTTP 层订阅它,经 SSE 推给所有连着的浏览器。看板也能回写(rewind)。

**为什么不那么做**(独立监控进程 + 文件监听):
- **真相一致性**:engine 的内存状态是唯一真相。看板和它同进程,读到的就是 live 数据,无需"读文件→推断状态"这一层。文件是落盘快照,和内存状态有写盘延迟;同进程读内存没有这个问题。
- **可回写**:独立进程只能读文件,不能触发 rewind(rewind 改的是内存状态)。同进程让看板的 rewind 按钮直接调 `engine.rewind()`,改完立即落盘 + 通知。
- **实时性**:文件监听(`fs.watch`)在 Windows 上跨平台可靠性差(rename 事件、递归限制),且是"写盘→内核事件→重绘"两跳。内存钩子是"状态变→直接推",一跳、亚秒级、平台无关。

**为什么不那么做**(上 WebSocket):SSE 是单向推送(server→浏览器),对"看板"这个场景足够(状态变更推过去,操作用普通 POST)。WebSocket 的双向能力在这里用不上,反而要处理握手/心跳/重连协议。**SSE 自带断线重连(EventSource 浏览器原生),更简单。**

**关键纪律**:HTTP server 启动失败时**只 stderr 警告,不让 MCP server 挂**——MCP(stdio)是主功能,看板是附加体验。两者解耦,看板坏了不影响 agent 调工具。

## 明确不做(守聚焦)

这些功能每次都会有人要,我们每次都要解释为什么不加:

| 功能 | 为什么不做 | 现有替代 |
|------|-----------|---------|
| 声明式条件表达式(`${{ }}`/`when:`/`if:`) | 引入表达式引擎 = 复杂度悬崖,且 agent 判断力比表达式强 | agent 用 `next_step_id` 显式跳转 |
| 自动循环(while/until) | goto 已能表达循环,且由 agent 驱动更灵活 | `report_step_result(..., next_step_id)` 回退到循环起点 |
| 超时 / 定时器 / cron | 这是批处理调度器的领域,和"人在环里"的定位冲突 | 用 Temporal / Airflow / cron 外部触发 |
| 子工作流 / 嵌套调用 | 增加状态管理复杂度,收益不明 | 把子流程写成独立 YAML,或在一个工作流里平铺 |
| 数据库 / Web UI / 监控仪表盘 | 见决策 5;UI 是独立项目,不进核心 | `list_runs` + `get_run_status` 文本够用 |
| 自动执行 skill(无需 agent 调用) | 这破坏了"agent 是唯一执行者"的模型,且 skill 是交互式的 | server 只编排,agent 在对话里调 skill |
| 热加载工作流(运行中改定义) | 已运行的 run 绑定了它启动时的定义快照,改定义会让状态不一致 | 改定义后用新 YAML `start_workflow` 开新 run |

## 兼容性承诺

**所有新能力都是加性的,默认退回旧行为。** 一个不含任何新字段(`group`/`max_attempts`/不传 `status`/不传 `next_step_id`)的旧 YAML,跑出来的状态轨迹和 v0.0.1 逐字节一致。

这是设计纪律,不是巧合:
- `StepState.attempts` 默认 0,不传 status 时永不递增。
- `RunState.activeStepIds` 默认 undefined,线性模式从不写入。
- 泛化后的 GUARD 在单元素活跃集时和旧 GUARD 逐字等价。
- `loadAll()` 给历史落盘文件回填缺失字段,老 run 重启后照常可用。

**证据**:v0.1.0 共 106 个测试,其中 51 个是 v0.0.1 的旧断言,**零改动**仍全绿。
