> **实验对象**: MCP-native 有状态工作流编排 server(路线 B)
> **实验性质**: 1 天 spike,目标是用最小实现回答三个赌注,决定值不值得做成产品

## 🏁 项目状态:已结项(spike 圆满完成,未进入产品阶段)

**这个项目到此为止,以"验证完毕"收尾,不是半途而废。**

- **想法**:能否用 MCP server 把工作流编排做成"有状态、可审计、不绑特定 agent"?
- **结论**:**技术机制完全可行**(协议层 + 逻辑层 + agent 行为层三层验证通过)。
- **意外发现**:机制可行 ≠ 值得做产品。实测证明,B 只在**"流程可审计/可恢复/可版本化"**场景结构性胜出;**个人"把事做完"的场景,A(菜谱)够用,B 是过度工程**。
- **当前定位**(发起者真实目的是"验证想法"):目的已达成,需求不支撑产品级投入 → **收手**。

### 什么情况下重启这个项目?

1. **出现真实可审计场景**:团队标准化流程 / 合规审计 / 长流程必须可恢复 —— B 从"过度工程"变成"刚需"。
2. **MCP 有状态 server 规范落地**:见 MCP 官方 [issue #2925](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/2925)。规范一定,这套本地实现是最接近的参考。
3. **发起者真实需求转变**:从"验证想法"变成"我/团队每天要用"。

重启时的第一步:跳到本文档底部的「下一步建议」,从"自用一周"的真实流程验证开始,而不是直接进产品开发。

## 三个赌注的验证结果

### 赌注 1:菜谱(方式 A)够不够用?—— ✅ 实测验证,**不够**(在"可恢复/可审查"维度)

本轮做了 A vs B 真实对照(同主题"远程工作利弊",同 4 步流程):

| 维度 | 方式 A(菜谱)实测 | 方式 B(状态机)实测 | 差距 |
|---|---|---|---|
| 断点恢复 | ❌ 打断后无机制从中间续 | ✅ `get_run_status` + `report` 精确恢复 | **明显** |
| 执行可审查 | ❌ 4步串成一整段文本,无中间态 | ✅ 每步状态/输出/时间戳/调用轨迹 | **明显** |
| 过程可 diff | ❌ 产物是连贯文本,无法逐步diff | ✅ callLog + steps 结构化记录 | **明显** |
| 确定性 | ⚠️ agent 可能用不同措辞/顺序组织 | ✅ 顺序由 server 锁定 | **明显** |
| **完成质量** | ✅ 同样能把任务做完 | ✅ 同样能把任务做完 | **打平** |

**关键发现(诚实)**:在**"能不能完成任务"**上,A 和 B **打平**——A 一样能产出高质量结果,而且**更快**(一次性串完 vs 5 次工具往返)。

**B 的优势集中在"过程质量"而非"结果质量"**:只有当你**需要可恢复、可审查、可版本化、确定性的流程**时(团队标准化、审计、合规、长流程),B 才是刚需。如果只是个人"把事做完",A 够用,B 反而慢。

**这正面回答了上一轮最大的疑虑**:当初担心"B 是不是过度工程"。答案是——**取决于使用场景**。B 不是对所有场景都赢,但对"流程化/可审计"场景是结构性赢。

### 赌注 2:MCP 工具驱动状态机顺不顺?—— ✅ 验证通过(协议+约束+行为三层)

这是本次**验证得最扎实**的赌注。四轮测试:

| 测试 | 结果 | 证明了什么 |
|---|---|---|
| 引擎逻辑自测 | ✅ 15/15 | 推进、跳步守卫、断点恢复,逻辑正确 |
| MCP 协议级自测 | ✅ 10/10 | 裸 JSON-RPC 全链路(initialize/list/call)畅通 |
| **混沌 agent 测试** | ✅ **7/7** | **状态机能死死管住乱来的 agent** |
| **真实 agent 闭环** | ✅ **4/4 步全通** | **agent 配合度完美,无卡顿无报错** |

混沌测试是关键:我模拟了一个"捣乱 agent",尝试了四种作恶方式——**全部被状态机拦截**:

1. 跳过当前步报未来步 → ❌ 拒绝
2. 编造不存在的 step_id → ❌ 拒绝
3. 重复报已完成的步 → ❌ 拒绝
4. 乱序跳步(a 之后直接报 c) → ❌ 拒绝

**只有乖乖按 `a→b→c` 顺序才能推进。** 状态机的约束力**不依赖 agent 自觉**,是 server 端强制的。

真实 agent 闭环(本轮补做的关键数据点):我作为真实 agent 被状态机驱动走完 4 步全程,**5 次工具调用(1 start + 4 report),无一跳步、无一合并、零报错**。关键观察:**状态机没有让 agent 卡住——它"给一步做一步"的节奏,和 agent 的工作方式天然契合**。这是对"agent 会不会嫌约束太死而卡住"这个疑虑的直接证伪。

### 赌注 3:可移植性 / context —— ✅ 协议层验证通过

| 验证项 | 结果 |
|---|---|
| server 不绑特定客户端 | ✅ 用裸 JSON-RPC 直连,任何 MCP 客户端都走这套协议 |
| 状态放 server 端,不进 agent context | ✅ 状态在 `Map<run_id, RunState>`,只在工具返回时按需传一小段文本 |
| 跨客户端可跑 | ✅ 协议级成立;已注册进 Claude Code(`workflow-sm ✔ Connected`) |

**与原方案的对比**:原 `feasibility-report.md` 里"方案 C(prompt 注入)"被评为 ★☆☆☆☆(不可靠),因为它靠 agent 自觉。路线 B 用 MCP 工具调用替代了 prompt 注入,**把"请你按顺序做"变成了"你只能按顺序做"**——确定性从"软约束"升级成"硬约束"。

## Go / No-Go 判定

### Go(技术机制层面)— 成立,无遗留悬而未决项

核心机制(状态机 + MCP 工具驱动 + server 端状态)**完全可行**,且解决了原方案回避的根本问题(自建运行时 vs 白嫖原生运行时的两难)。它既不锁死 Claude Code(可移植),也不依赖 agent 自觉(硬约束),还顺手解决了 context 爆炸(状态在 server 端)。

### 但产品层面有一个必须想清楚的前提

**目标场景是不是"流程化/可审计"?** 本轮实测发现一个**意外但重要的结论**:在"完成质量"上,B 和 A 打平,B 甚至更慢(5 次往返 vs 一次串完)。**B 只在"过程可恢复/可审查/可版本化/确定性"上结构性胜出**。

- 如果你的目标是个人"把事做完" → **B 是过度工程,A 够用,别做**
- 如果你的目标是团队标准化 / 审计 / 合规 / 长流程可恢复 → **B 是刚需,这是真空白**

另外即便机制成立,路线 B 仍是"自建运行时"——这是原 `feasibility-report.md` 当初判为 ★★☆☆☆(工程量大)而回避的路。机制验证通过了,但**产品阶段的并行/条件/循环/重试/持久化/监控工程量没变,那才是大头**。
