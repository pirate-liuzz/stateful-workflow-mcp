# 一次把 Agent 的流程“管住”的实验：workflow-sm 实验报告

> 本文是一次本机技术实验记录，不是第三方认证、法律审计意见，也不代表产品已经覆盖所有 Agent、所有桌面端或全部合规要求。

很多人以为，给 Agent 一份足够详细的提示词，它就会照着做完。

实际使用里，更常见的情况是：它跳过了中间核验、重复提交了已经完成的步骤；窗口一关，刚才做到哪里也很难说清；出了问题以后，只能翻聊天记录猜它到底做过什么。

我想验证一件小而具体的事：**能不能把“下一步该做什么”，从 Agent 的记忆和自觉里拿出来，交给一个独立的状态机来约束？**

这就是 workflow-sm 的起点。

## 01. 这次实验要验证什么

workflow-sm 是一个通过 MCP 接入的有状态工作流引擎。它不替 Agent 做调研、写作或改代码；它做的是保存流程状态，并只把当前允许执行的那一步交给 Agent。

本次实验只验证四件事：

1. Agent 是否无法越过当前步骤直接“交后面的作业”；
2. 流程在中断后，是否能保留进度和已经产出的内容；
3. 工作流状态是否能被看板实时看见；
4. MCP 工具、重试、跳转、并行前置步骤等核心能力是否能稳定工作。

没有验证的内容也要先说清：本次不是 Claude、Codex、ZCode 三个客户端的横向性能测评；不是自动化 Agent Runner 实验；更不是一份可以用于司法或法律审计的完整证据链。

## 02. 实验环境与载荷

实验在本机完成，使用项目内置的四步 YAML 流程 `research-to-report`：

| 顺序 | 步骤 | 任务 |
| --- | --- | --- |
| 1 | research | 产出 3 条关键事实 |
| 2 | analyze | 基于事实提炼 2 条洞察 |
| 3 | draft | 基于洞察起草 100 字内段落 |
| 4 | save | 确认并保存最终产物 |

MCP 层对外暴露五个工具：`start_workflow`、`report_step_result`、`get_run_status`、`list_runs`、`rewind`。状态机负责判断哪一步可以报告；Agent 仍然是具体任务的执行者。

![图 1：实验用四步 YAML 流程定义](./公众号素材/workflow-sm-YAML流程.svg)

*图 1｜实验用四步 YAML 流程定义。重点是四个 step id：`research`、`analyze`、`draft`、`save`。*

这里不是让模型“记住顺序”，而是把顺序写进状态机。

## 03. 实验一：故意让 Agent 乱来

最关键的一组实验，不是看正常流程能不能走通，而是故意让调用方违反规则。

实验依次尝试了四种常见错误：

| 故意的错误行为 | 结果 |
| --- | --- |
| 第一步还没完成，直接报告第二步 | 被拒绝 |
| 报告一个不存在的步骤 ID | 被拒绝 |
| 第一步完成后，再次报告第一步 | 被拒绝 |
| 完成第一步后跳过第二步、直接报告第三步 | 被拒绝 |

之后按 b → c 的正确顺序报告，流程才能走到完成。对应的混沌测试共 7 项，全部通过。

这其实是这次实验最重要的结论：**workflow-sm 不判断 Agent 写得好不好，但会阻止它把流程事实说乱。**

![图 2：本轮终端实验结果](./公众号素材/workflow-sm-终端实验结果.svg)

*图 2｜本轮终端实验结果。重点保留“跳步被拒绝”“重复报告被拒绝”“正确顺序完成”三类行为。*

“乱来的 Agent”不是靠提醒被劝住，而是被状态机的当前活跃步骤集合拒绝。

## 04. 实验二：窗口关掉以后，还能不能继续

第二组实验模拟中断。

1. 启动一条工作流；
2. 完成前两步，停在第三步；
3. 将运行状态写入本地持久化目录；
4. 重启引擎；
5. 重新读取运行记录，并继续完成剩余步骤。

结果是：工作流名称、前两步的完成状态、第三步的运行状态、前两步的输出和当前索引均被恢复；随后可以继续推进至完成。这组持久化与查看器同步测试共 23 项，全部通过。

它解决的不是“模型有没有记忆”，而是更朴素的问题：**一次任务在不同会话、不同时间点之间，是否还有一个可核对的进度事实。**

## 05. 实验三：把进行中的流程放到看板上

## 06. 汇总结果

本轮重新执行的验证如下：

| 验证模块 | 通过数 | 观察到的结论 |
| --- | ---: | --- |
| 核心状态机 | 17 | 顺序推进、拒绝跳步、倒带恢复正常 |
| 持久化与查看器同步 | 23 | 中断后可恢复状态与输出 |
| 混沌 Agent | 7 | 越级、虚构步骤、重复报告、乱序均被拒绝 |
| MCP 协议 | 12 | 初始化与 5 个工具可正常调用 |
| 重试与跳转 | 27 | 重试耗尽、成功后推进、显式跳转均受控 |
| 并行前置步骤 | 33 | 同组并行、汇合、倒带逻辑正常 |
| 看板与 SSE | 28 | 实时状态、倒带、删除、接口校验正常 |
| **合计** | **147** | **本轮验证全部通过** |

这里的“147 项通过”只说明这 147 个已编码场景的行为符合预期，不等于系统在真实复杂业务中已经没有风险。尤其是长链路 Agent 行为、权限治理、外部系统操作和审计证据完整性，还需要独立的场景测试。

## 07. 这项实验的意义，和它还不是什么

如果把 Agent 比作能干但会 improvisation 的同事，workflow-sm 不是替它工作，也不是给它打分；它更像一张不能跳过的流程卡：先做哪一步、下一步是谁、做到哪里、能不能回退，都由外部状态来确认。

这对以下场景尤其有价值：

- 需要多人或多会话接力的复杂任务；
- 需要强制复核、不能跳过核验环节的流程；
- 希望把“任务进行到哪里”从聊天记录里抽出来的团队；
- 未来要做 Agent 编排、风险控制或审计留痕的团队。

但边界同样清楚：它目前不替你判断产出质量；不会自动把所有桌面端 Agent 变成受控执行器；也还没有形成覆盖身份、授权、完整输入输出、外部系统操作的法律级证据链。桌面端与不同 MCP 客户端能否稳定执行整套协议，仍需要逐个客户端实测。

## 08. 下一步，我想请你一起挑刺

这轮实验先证明了“顺序、断点、可见性”可以被状态机接住。下一步最值得做的，不是堆更多功能，而是把它放进真实任务里：代码发布前检查、合规材料整理、研究报告协作，或者任何一步都不能漏的工作。

如果你正在用 Claude、Codex、ZCode 或其他 Agent 工具，我特别想听三个问题：

1. 你最不希望 Agent 跳过的是哪一步？
2. 你的任务中，哪一次中断最难恢复？
3. 你觉得“状态记录”至少要留到什么粒度，才真的有用？
